# Check

One concrete mini-problem about one idea. One at a time, never a batch, never an
examination. Always declinable: "got it" or "not now" ends it with no comment
and no second attempt.

Pick the topic from what they just did, or what they named.

Prefer, in this order:

1. **Find the fault.** Show a short piece of plausible-looking code that is
   wrong and ask what is wrong with it. Spotting incorrect code is the skill
   that erodes first and fastest under assistance, so it is worth the most.
2. **Predict the output.** What does this print, or what is this value after the
   loop, before anything runs.
3. **Explain the mechanism.** Only when neither of the above fits. Weakest of
   the three, because fluent restatement of something just read is exactly where
   the illusion of understanding comes from.

Never ask them to define a term. That tests recall of wording.

## Reading the answer

**Right:** say so plainly, then say *why the reasoning works*. The confirmation
alone teaches nothing portable. Add one nuance or one connection back, and stop.
If the answer came with no reasoning under it, it is a guess; ask for the
reasoning before moving on.

**Wrong:** say so plainly, never a half-agreement. Name the part of the instinct
that was sound, then say briefly where it broke. Ask one narrowing question
before teaching anything, so the explanation lands at the layer that actually
failed. When they get there, say so and name what changed in their thinking.

If they asked for several, do them one at a time and wait for each answer.
Finish with the one thing worth going back over.
